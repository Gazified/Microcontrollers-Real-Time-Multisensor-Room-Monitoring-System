BCA152 Technical Checkoff Study Guide

ESP32 FreeRTOS Multisensor Room Monitoring System

Core explanation: The system uses six FreeRTOS tasks. SensorTask acquires data and distributes it through dedicated queues; MotionTask and AlarmTask publish events through an event group; a mutex protects shared serial output; and deterministic logic is verified by 13 native unit tests.

Technical Defense Questions

1. Why did you create SensorTask?

SensorTask periodically reads the DHT22 temperature and humidity and the LDR light level. It stores the values in SensorData and sends the latest reading to DisplayTask and AlarmTask. It executes every two seconds with vTaskDelayUntil().

2. Why does each task have its assigned priority?

  • MotionTask and InputTask: priority 3 for prompt motion and encoder response.
  • SensorTask, AlarmTask, and StateTask: priority 2 for measurements, safety evaluation, and state management.
  • DisplayTask: priority 1 because display refresh can tolerate small delays.

3. What does vTaskDelayUntil() do?

It blocks a task until its next scheduled wake time. It maintains a regular two-second sampling period and reduces timing drift compared with repeatedly delaying after sensor work completes.

4. What happens to a task while it is delayed?

It enters the Blocked state and does not consume CPU time. When the delay expires, it becomes Ready and waits for the scheduler to run it.

5. What information crosses your queue?

struct SensorData {
    float temperature;
    float humidity;
    int lightLevel;
    bool motionDetected;
};

This structure is sent through separate display and alarm queues.

6. Why use a queue instead of unsynchronized global variables?

A queue safely copies data between tasks and provides synchronization. A shared variable could be read while another task is modifying it. Two queues are used because receiving an item removes it from a FreeRTOS queue; this prevents DisplayTask from stealing AlarmTask's data.

7. What resource does your mutex protect?

The mutex protects shared serial output inside safeSerialPrintf(). It prevents diagnostic messages from multiple tasks from becoming interleaved and unreadable.

8. Where could a race condition occur?

Multiple tasks could write to serial output simultaneously without the mutex. InputTask also updates gCurrentDisplayMode while DisplayTask reads it; this is a shared state that must remain simple or be synchronized if it becomes more complex.

9. What does your event group represent?

EVENT_ACTIVE  = BIT0
EVENT_MOTION  = BIT1
EVENT_ALARM   = BIT2

These bits represent active system state, PIR motion, and an out-of-range temperature alarm. Tasks set or clear them, and DisplayTask uses them when rendering the OLED.

10. Which task owns the OLED, and why?

DisplayTask owns the OLED. This prevents multiple tasks from writing to the I2C display at the same time. Other tasks communicate through queues or shared state instead of directly controlling the OLED.

11. What happens if a high-priority task never blocks?

It can monopolize the CPU, starve lower-priority tasks, increase CPU usage, and make the display, sensors, or input unresponsive. The project avoids this by using delays and queue waits.

12. What is the difference between Ready and Blocked?

A Ready task can run but is waiting for CPU time. A Blocked task is waiting for a delay, queue data, semaphore, or event. AlarmTask is blocked while waiting in xQueueReceive(..., portMAX_DELAY).

13. What did your unit tests verify?

The 13 native tests verify five temperature alarm cases, four display navigation cases, and four ACTIVE/INACTIVE state cases. They test hardware-independent decision logic, not the physical buzzer, GPIO, OLED, or DHT22. Those are verified in Wokwi.

14. What did static analysis discover?

The native analysis passed. The ESP32 cppcheck run was marked failed because cppcheck has difficulty parsing some ESP-IDF/Xtensa-specific headers and generated configuration. This is separate from compilation: the ESP32 firmware build succeeds. The result must be reported honestly rather than claimed as a complete pass.

15. What would differ on physical hardware?

Physical hardware requires flashing and real wiring. Readings may be noisier, DHT22 timing and I2C wiring may require troubleshooting, and buzzer loudness depends on the actual component. The FreeRTOS architecture remains the same, but Wokwi is more idealized than real hardware.

Important Evidence

  • Six FreeRTOS tasks are created in src/main.cpp.
  • Sensor data is defined in include/sensors.h.
  • Queues, mutex, and event group are initialized in src/rtos_objects.cpp.
  • Periodic sampling uses vTaskDelayUntil() in src/sensors.cpp.
  • Unit tests are in test/test_main.cpp.
